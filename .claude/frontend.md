### 画面遷移

```
/login ──(認証成功: hr)──> /home ──(行クリック)──> /inbox/:roomId
   │     └─(認証成功: student)──> /mypage ⇄ /chat  └─(サイドバーの受信箱)──> /inbox
   │                              /students ──(カードクリック)──> /inbox/:roomId
   └──(未登録)──> /register

未認証で保護ページへアクセス → /login へリダイレクト（元URLを query に保持）
```

**ログイン後の遷移先は `useAuthStore.homePath` の1箇所に集約する。**
LoginView・ルーターガード・ナビレールはいずれもこの getter を参照し、パスを直書きしない。

## 2. ルーターガード ★最重要の修正点

**現状の実装（`router/index.js`）は「login 画面から遷移してきたか」しか判定しておらず、リロードで必ず弾かれる。**
以下の**認証状態ベース**に置き換えること。

```js
router.beforeEach(async (to) => {
  const auth = useAuthStore();
  // 未初期化なら /api/auth/me の解決を待つ（リロード直後の対策）
  if (!auth.initialized) await auth.fetchMe();

  if (to.meta.requiresAuth && !auth.user) {
    return { path: '/login', query: { redirect: to.fullPath } };
  }
  if (to.path === '/login' && auth.user) {
    return auth.user.role === 'student' ? '/chat' : '/inbox';
  }
});
```

受入条件：**ログイン後に F5 でリロードしてもログイン画面に戻されないこと。**

## 3. Pinia ストア設計

`provide/inject` のバケツリレーは全面的に廃止する。

| ストア | 責務 |
| --- | --- |
| `useAuthStore` | `user`, `initialized`, `login()`, `logout()`, `fetchMe()` |
| `useRoomsStore` | `rooms`, `filters`, `sortKey`, `summary`, `sortedRooms`(getter), `upsertRoom()`, `applyFilters()` |
| `useMessagesStore` | `byRoomId`（ルームIDをキーにしたキャッシュ）, `hasMore`, `loadHistory()`, `appendMessage()`, `markSent()`, `markFailed()` |
| `useUiStore` | 選択中ルームID、パネル開閉、スニペットパレットの表示状態、会社情報（P2-10） |
| `useSchedulesStore` | 面接官、予約依頼、最新空き枠、選択中枠、Socket更新（P3-4） |

### ルール

- **フィルタ・ソート条件は `useRoomsStore` に保持する。** ルーム切替で失われないこと
- **メッセージは `byRoomId` にキャッシュし、ルーム再訪時に再フェッチしない**
- Socket イベントによる更新も必ずストアの action 経由で行う
- 基盤ストアは従来の4つを維持し、改訂版P3-4だけは独立した予約ライフサイクルを持つため
  `useSchedulesStore` に分離する。定型文（`snippets`）・会社情報（`company`）のような
  ルームに紐づかない全社共有マスタデータは `useUiStore` に置く。予約以外の都合でストアを増やさない

## 4. Socket の扱い

**`composables/useSocket.js` を Socket.IO イベントの唯一の入口とする。**

```
useSocket.js
  ├ socket.on('message:new')    → messagesStore.appendMessage() + roomsStore.upsertRoom()
  ├ socket.on('message:sent')   → messagesStore.markSent()
  ├ socket.on('room:updated')   → roomsStore.upsertRoom()
  ├ socket.on('read:updated')   → messagesStore.updateReadState()
  ├ socket.on('memo:updated')   → memo の反映
  ├ socket.on('summary:updated')→ roomsStore.summary の更新
  ├ socket.on('schedule:slot_updated') → schedulesStore.handleSlotUpdated()
  └ socket.on('schedule:request_updated') → schedulesStore.handleRequestUpdated()
```

- **コンポーネント内で直接 `socket.on()` を書かない**
- 切断時は指数バックオフで自動再接続し、再接続後に各ルームの差分を REST で再取得する

### 縦割りの軸（列）

- 既定は**対応ステータス**（ログイン直後に「返信すべき学生」から見えることを優先する）
- `縦割り` の切替ボタンで **対応／選考／AI推奨度** を選べる。状態は `useUiStore.boardGroupBy`
- **その列に学生が0人でも列は出す。** どの段階が空いているかも情報のため
- 列が 1280px に収まらないときは**ボードごと横スクロール**する（縦は列ごとに独立してスクロール）

### カードに表示する項目

① アバター／② 氏名／③ **縦割りに使っていない残り2つのステータス**のチップ
／④ 経過時間バッジ／⑤ 新着メッセージの有無（点）

- **大学名・最新メッセージは載せない。** 1枚が高くなると「上から順に処理する」俯瞰性が落ちるため
- 新着は**件数を出さず点だけ**で示す（読み上げには件数を残す）
- AI推奨度が高いカードは左端にアクセントを付ける。ラベルはAI推奨度チップが担う。
- **学生番号（`ST-2024-089` のような表示用ID）は持たない。** `students` テーブルに該当カラムが無い

### 並び順

**並び替え UI は持たない。** 列の中は常に `AI推奨度（高→低） → 経過時間の長い順` で固定する
（コンセプト「返信すべき学生が、上から順に並んでいる」）。フィルタは P1-7 で有効化する。

### AI 現況サマリー（P3-1）

- 右カラム（320px）に **AiSummaryCard** を置く。`useUiStore.aiPanelOpen` で開閉する
- 起動用の **AI ボタンは画面右下に固定した円形ボタン（FAB）**。チャットボット起動ボタンと同じ体裁
- データの置き場は `useRoomsStore.aiSummary`（サーバ由来のデータなので ui ストアには置かない）
- 仕様の詳細は `business-logic.md` §7-2、エンドポイントは `api.md` を参照

## 5-3. 全学生画面レイアウト（S-08）

受信箱（S-03/S-04）とホーム（S-07）は担当制で自分の担当学生しか出さないため、
**担当外・未配属も含めた全学生**をここで俯瞰する。**対応漏れの拾い上げが目的の画面。**

```
┌────────────────────────────────────────────────────────────────┐
│ 全学生                    [緊急 5] [要返信 12] [24h超 3]  [氏名・大学で検索]  │
│ 担当外・未配属も含めた全学生を、担当人事ごとに並べています                    │
├────────────────────────────────────────────────────────────────┤
│ フィルター 対応▾ 選考▾ タグ▾ AI推奨度▾                    並び順▾   40件 │
├────────────────────────────────────────────────────────────────┤
│ 未配属 4      │ 田中課長 12   │ 佐藤 12      │ 鈴木 12      │ …（横スクロール）│
│ ┌──────┐ │ ┌──────┐ │ ┌──────┐ │ ┌──────┐ │              │
│ │鈴 鈴木一郎 ●│ │山 山本直樹 ●│ │小 小林蓮   ●│ │森 森田結衣  │ │              │
│ │[要返信]      │ │[対応中]      │ │[要返信]      │ │[完了]        │ │              │
│ │[一次面接][緊急]│ │[書類][通常]  │ │[二次面接][通常]│ │[内定][低]    │ │              │
│ │      ⚠26時間│ │      ⚠19時間│ │      ⚠15時間│ │              │ │              │
│ └──────┘ │ └──────┘ │ └──────┘ │ └──────┘ │              │
└────────────────────────────────────────────────────────────────┘
```

ホームとの違いは次の2点だけで、それ以外（ボードの体裁・カード・列内の並び）は共通
（`BoardColumns` を両画面で使う）。

| | ホーム（S-07） | 全学生（S-08） |
| --- | --- | --- |
| 対象 | 自分の担当のみ（`myRooms`） | **全件**（`allSortedRooms`） |
| 縦割りの軸 | 対応／選考／AI推奨度を切替 | **担当人事に固定**（切替 UI なし） |
| カードのチップ | 縦割りに使っていない2つ | **対応・選考・AI推奨度の3つ** |
| AI 現況サマリー | あり（P3-1a） | **なし** |
| 未対応サマリーバー | あり（自分の担当の件数） | あり（**全学生の件数**・`SummaryBar` の `scope="all"`） |

`SummaryBar` の件数は**その画面に出ているルームの範囲と必ず揃える**（`scope`）。
受信箱・ホームは自分の担当（`myRooms`）、全学生は全件（`rooms`）。ずれると
「あと何件残っているか」という役割が壊れる。どの画面でもクリックで共有のフィルタが掛かる。

### 列（担当人事）

- **未配属を必ず一番左**に置く。どの人事の受信箱にも出ていない学生の拾い上げが目的のため
- 続いて `GET /api/users?role=hr&role=admin` の順に人事の列を並べる。**担当0名の人事も列を出す**
  （誰に余裕があるか＝誰に振れるかも情報）
- 列の中の並びはホームと同じ `AI推奨度（高→低） → 経過時間の長い順`
- フィルタ・検索・ソートの条件は受信箱・ホームと共有する（`useRoomsStore.filters` / `sortKey`）

### 担当外の学生を開く

カードクリックで `/inbox/:roomId` を開く（返信はこの画面では行わない）。
`room_members` には**人事全員**が入っているため、担当外でもトークとプロフィールは開ける
（P2-4「担当外の人事がルームを開いても状況が把握できる」と同じ前提）。
一覧（`InboxSidebar`）は担当制のままなので、担当外のルームは左の一覧には並ばない。

## 6. UI 表現ルール

| 要素 | ルール |
| --- | --- |
| AI推奨度 | `high`＝行の左端にアクセント、`low`＝行全体を薄く表示 |
| 経過時間 | 12h以上＝黄、24h以上＝赤。`done`/`waiting_student` では非表示 |
| 未読 | 行の右端に青丸バッジ＋件数。行タイトルを太字化。**ホームのカードだけは件数を出さず点で示す**（§5-2） |
| 未アサイン | 担当者欄をオレンジ枠＋「未割当」 |
| 対応ステータス | `constants.md` の配色チップ。**クリックでドロップダウン → 1クリックで変更** |
| 空状態 | 「対応が必要な学生はいません 🎉」 |

**色だけで情報を伝えない。** AI推奨度・ステータスは必ずテキストラベルを併記する。

## 7. トーク画面（B-2）

- **吹き出し**：自分＝右寄せ（緑 `#3EA76B` 系）、相手＝左寄せ（白／グレー枠）
- 相手の吹き出し左横にアイコン（`avatar_color` の丸＋イニシャル）と名前。**連続発言時はアイコンを省略**
- 吹き出し外側に送信時刻（`HH:mm`）
- 日付が変わる位置に**日付セパレータ**（`2026年8月5日（水）`）
- **並び順は古い→新しい。** 初期表示は最下部へ自動スクロール
- **無限スクロール**：上端到達で `before` カーソルにより過去50件を追加読み込み。読み込み中は上部にスピナー、**スクロール位置を補正して表示位置がジャンプしないようにする**

### 送信状態（B-3）

```
送信中（薄字・時計アイコン） → 送信済（時刻表示） → 既読
```

- 送信時にクライアントで `clientMsgId`(UUID) を生成し**楽観的に描画**
- サーバの `message:sent` ack で確定
- **5秒以内に ack がなければ失敗扱い**とし、再送ボタンを表示
- 再送しても `clientMsgId` により重複保存されない

### 送信取消

自分のメッセージのみ、**送信から24時間以内**は取消可能。物理削除せず「メッセージの送信を取り消しました」とグレー表示。

## 6-2. 設定画面のセクション（S-06）

`/settings/profile` は**全ロールが入れる**（ルーターの `meta` は `requiresAuth` のみ）。
そのため**セクション単位でロールを出し分ける**。

| セクション | 対象 | 中身 |
| --- | --- | --- |
| プロフィール | 全員 | 表示名・ステータスメッセージ（B-5） |
| 定型文 | **人事のみ** | `GET /api/snippets` が人事限定（P2-1） |
| 会社情報 | **人事のみ** | 学生は `/chat` の `CompanyPanel` で閲覧するだけ（P2-10） |
| 選考フロー | **人事のみ** | 学生は `/mypage` のフロー図で見るだけ（P2-11） |
| アカウント | 全員 | ログインIDとログアウト |

- **セクションを足すときは「学生に出してよいか」を必ず判断する。**
  人事限定の API を叩くセクションを全ロールに出すと、学生の画面で 403 のトーストが出る
- 見出しと中身は**同じ `activeSection.key`** で描き分ける。選択中の key を直接見ると、
  自分に出ていないセクションの中身だけが描画されて見出しとずれる余地が残る

### 会社情報パネル（P2-10）

- **タブ（別画面）にしない。** 学生は情報を能動的に探しに来ないため、
  返信を待つ間に自然と目に入る位置に常設することを優先する
- 中身は人事が設定画面で入れた値をそのまま出すだけ。**学生は編集できない**
- データは `useUiStore.company`。取得は `ChatView` の `onMounted` で1回だけ（`fetchCompany()`）
- 未設定（`company: null`）でも画面が壊れないこと。パネルに1文出すだけにする
- 紹介文は改行で段落に分けて描画する。**`v-html` は使わない**（§10-1）
- 採用サイトへのリンクは `target="_blank"` ＋ **`rel="noopener noreferrer"`**（タブ乗っ取り対策）
- 情報が増えたらパネル内でスクロールさせる。トークの高さを押し広げない

### 会社情報の帯（`CompanyPanel layout="banner"`）

**主役は下の選考フロー。** 帯は「どの会社の選考か」を示すだけの静かな1行にする。

- `社名 ｜ 紹介文 ｜ 採用サイトのリンク` の3カラム。**高さが変わらないよう1行に収める**
- 紹介文は**先頭の1段落だけ**を出し、溢れたら `…` で切る（全文はチャット画面の縦パネルで読める）
- 「会社情報」の見出し band は出さない（社名自体が何の情報かを語るため）。
  読み上げ用に見出しは DOM に残す
- リンクは**ボタンにしない。** オレンジの面を置くとフローより先に視線を奪う

### 確定した面接のカード（`BookedInterviewCard`・P3-4）

学生が日程を予約したあと、その予定は**チャットの日程調整カードの中にしかなかった**。
前日に確認したい学生は着地点からチャットへ移り、過去のメッセージを遡る必要がある。

- **フロー図より上に置く。** フロー図が示すのは「いまどこにいるか」、
  このカードは「次に何があるか」。日付は当日が近いほど価値が上がる
- 出すのは**確定済みで、まだ終わっていない面接だけ**。判定はサーバ
  （`GET /selection-flow/me` の `upcomingInterviews`）。クライアントで絞り直さない
- 確定した面接が無ければ**何も出さない**。空のカードは情報量を下げるだけ
- 主役は日時。面接官・形式・場所は1行に流して差をつける
- 残り日数（`本日` / `明日` / `あとN日`）を**テキストで**添える。色だけで近さを伝えない
- 当日・翌日のときだけ左のオレンジの帯＋クリームの面に切り替える。
  未読のチャットカード・FBカードと同じ言語（オレンジの帯＝自分に関わる新しいこと）に揃える
- **会議室・URLが未設定の状態は正常。** 人事があとから決める（未設定のまま日が近づくと
  人事に通知が飛ぶ：P4-5）。空欄で出さず「担当者からご連絡します」と書く
- **予約・変更の操作は置かない。** 日程の相談はチャットの仕事で、
  ここに操作を置くと日程調整カードと役割が二重になる

### 表示のルール

- **状態は3つ**
  | 状態 | 丸 | つなぎ線 |
  | --- | --- | --- |
  | 完了 | オレンジの枠＋薄いオレンジの面＋チェック | **オレンジ**（歩いてきた道） |
  | 進行中 | オレンジの塗り＋白文字＋一回り大きく＋影＋リング | — |
  | これから | 薄いグレーの枠＋白い面 | **薄いグレー** |
- **現在地は「山の頂上」として持ち上げる。** 形は正規分布（ガウス関数）そのもの
  （下記）。裾野が平ら、肩がなめらか、頂点が丸い曲線になる
- **「いまは○○の段階です」という一文は置かない。** 現在地は図が示すので、
  同じことを文章でも言うと視線が二重になる
- **色だけで状態を伝えない。** 進行中は画面にラベルを出し、残りは `sr-only` で持たせる
- 番号を振るのは、選考が**順序に意味のある本物の手順**だから
- 完了ステップにFBが届いていれば丸の**左上**に点を出す（読み上げにも「フィードバックあり」を残す）。
  右上は面接アンケートの吹き出しタグが使うので譲る
- 既定で**現在地の詳細を開いた状態**で着地する。学生がまず知りたいのは「いま」のこと
- 辞退した学生にはフロー図を出さず、終端の文言に切り替える
- 図に並ぶのは「有効なステップ」だけではない。**その学生の現在地とFBのあるステップは
  無効でも差し込まれる**（`business-logic.md` §8）。人事が設定を変えても現在地が図から
  消えないようにするため。消えると山の頂点が決まらず線がまっすぐになる

### つなぎ線の描き方 ★実装上の注意

**線は SVG のパス1本として描く。** 丸ごとに疑似要素（`::before` / `::after`）で
引いてはいけない。理由は2つ。

1. 疑似要素は DOM 順で丸より後に描画されるため、**線が丸の上に重なる**
2. 持ち上げた「山」の形に線を追従させられない

### 山の形は1つのガウス関数から出す

```
lift(x) = -PEAK_LIFT × exp( -(x - 頂点x)² / (2σ²) )      σ = 丸の間隔 × 0.8
```

**丸の持ち上げ量も線の高さも、この同じ式から出す。** そうすることで
線は必ず丸の中心を通り、ズレようがない。

- **曲線は細かく標本化した折れ線（4px 刻み）で描く。** 丸から丸へベジェで繋ぐと
  「区間ごとの S 字」になり、裾野が膨らんで正規分布に見えない
- σ を丸の間隔に対する比で持つので、ステップ数や画面幅が変わっても
  山のなだらかさは一定になる
- 現在地が無い（内定・辞退・未設定）ときは山を作らず、まっすぐな線にする

### 測るときの注意

**持ち上げる前の位置を測る。** 持ち上げは `transform` で与えるため、持ち上げ後の丸を
測ると「測った値 → 持ち上げ量 → 測った値」の循環になる。
`transform` が掛かっていない親（ボタン）を基準にして循環を断つ。

- 線は `z-index: 0`、丸は `z-index: 1` で**明示的に**重なり順を決める
- 幅の変化は `ResizeObserver` で拾って引き直す
- 通過済み（オレンジ）とこれから（グレー）は**別のパス**として描き、現在地の中心で接続する
- `.flow` に `overflow-x: auto` を指定すると `overflow-y` も `auto` に計算されるため、
  持ち上げたぶんの余白（`--lift-clearance`）を上に取らないと丸とリングが切れる

### アニメーション

**体感を止めないことを最優先にする。**

- 丸は 1つあたり 35ms ずらして 180ms で立ち上げ、**全体で 500ms 以内**に収める
- 遅延は8番目で頭打ちにして、ステップが増えても待ち時間が伸びないようにする
- 動かすのは `transform` と `opacity` だけ（レイアウトを動かさない）
- 入場は**マウント直後の1回だけ。** 詳細を開くたびに再生しない
- 通過済みの線は `pathLength="1"` で正規化して 320ms で引く（ステップ数や画面幅に依存しない）
- 現在地のリングだけ 2.4s のゆるいパルスを残す（迷子にならないための目印）
- `prefers-reduced-motion: reduce` で入場・パルスとも止める

### データ

- `GET /selection-flow/me` の**1回**でステップ・現在地・FB をまとめて取る（往復を増やさない）
- 選考ステータスは人事がいつでも変えるので、この画面は**開くたびに取り直す**
  （会社情報はマスタデータなので初回のみ）
- **FB を見せてよいかの判断はサーバが持つ。** クライアントで隠す作りにしない
- 本人のメモ（S-10）も同じレスポンスに載る（各ステップの `note` と `overallNote`）
- 確定した面接（P3-4）も同じレスポンスに載る（`upcomingInterviews`）。
  日程だけ別のAPIに取りに行かせない

### ステップ詳細の2カラム（`SelectionStepDetail`）

```
┌─ 二次面接                                    [進行中] ─┐
│ ┌── 読むもの ────────┬── 自分に固有のもの ──┐ │
│ │ この選考について      │ 企業からのフィードバック │ │
│ │ （本文）              ├──────────────────────┤ │
│ │ ─────────────       │ このステップのメモ       │ │
│ │ ポイント              │ （自動保存の textarea）  │ │
│ │ ・…  ・…             │                          │ │
│ └───────────────────┴──────────────────────┘ │
└────────────────────────────────────────────────────┘
```

- **列は情報の性質で割る。** 左＝会社が全員に用意した「読むもの」、
  右＝その学生に固有の「受け取るもの・書くもの」。縦に積むと会社の説明と
  自分への評価が同じ流れに見えてしまう
- ポイントは**面で囲まずリストとして組む。** 行頭にオレンジの点を置くだけで、
  カードを重ねずに列挙だと分かる
- FB は左にオレンジの帯を持つカード。面はクリームに留める
  （オレンジのベタ面は本文より先に視線を奪う）
- 900px 以下では1カラムに畳む

### チャットへの導線（`StudentChatCard`）

マイページはログイン後の着地点なのに、チャットへの入口がナビレールの1項目しか無く、
**しかもそれが新着を知らせていなかった。** 人事からメッセージが来ても学生が気づけない。

- ナビレールの「チャット」に**未読件数のバッジ**を出す（人事の通知バッジと同じ `.rail__badge`）
- マイページ下段を2カラムにし、全体メモの右に**チャットカード**を置く
  - 担当人事名 ｜ 最新メッセージの抜粋（`LAST_MESSAGE_PREVIEW_LENGTH`）｜ 未読件数
  - 自分の発言なら「あなた：」を前置する（誰の発言か分からないと抜粋が読めない）
  - 未読があるときだけ左にオレンジの帯（FBカードと同じ言語に揃える）
  - **返信はここでしない。** 入力欄を置くとチャット画面と役割が二重になる
- データは `GET /rooms` の `unreadCount` / `lastMessage` / `assignee`。**専用APIを作らない**
- リアルタイム更新はスコープ外。マイページを開いた時点の状態を出す
- **マイページを開くたびに `fetchRooms()` を呼ぶ（取得済みでも省略しない）。**
  `room:updated` はサーバが `io.in('hr')` にしか配信しておらず、学生のストアは
  socket では最新化されない。省略するとチャットで既読にして戻っても未読件数が残る

### 学生メモ（S-10・`StudentNoteEditor`）

**粒度は2つ。** ステップ別（詳細の右カラム）と全体（フローカードの下の独立カード）。
「二次面接で聞きたいこと」はステップに紐づき、「企業研究」はどのステップにも属さないため。

- **自動保存。** 入力停止から 800ms でPUT。`blur` と unmount 時は即座に送る
- **ステップを切り替えるときは、切り替え前に必ず送る。** 書きかけを消さない
- 保存の状態は「保存中… / 保存しました」の控えめなテキストのみ。
  失敗時はトーストを出し、**入力中の本文は消さない**
- フロー図の丸に「メモあり」の目印は出さない（FBの点と競合して意味が読めなくなる）
- **人事には見えない。** 人事側の画面にこのコンポーネントを置かないこと

### 面接アンケート（バッジ＋回答カード）

★現時点では**フロントエンドのみのモック**。バックエンド（永続化・API）は未実装で、
回答状態は `StudentHomeView` のローカル状態（`Set`）に置く。リロードで消える。

**対象ステップ**：面接系のステップ（`statusKey` が `interview_` で始まるもの。一次〜五次面接）。

**表示条件**：ステップの `state` が「完了」かつ、そのステップのアンケートが未回答のとき。
「進行中」「これから」の段階ではバッジもカードも一切出さない。

**① バッジ（`SelectionFlow.vue`）**

- 対象ステップの丸の**左上**に小さな赤丸バッジを出す（既存のFB印は右上なので衝突しない）
- 色は `var(--color-error)`。色だけで終わらせず `sr-only` で「アンケート未回答」を持たせる
- バッジ付きのステップをクリックすると、詳細エリアへ切り替わった後
  アンケートカード（`#survey-card`）まで `scrollIntoView({ behavior: 'smooth' })` する。
  `prefers-reduced-motion: reduce` では `behavior: 'auto'`

**② 回答カード（`InterviewSurveyCard.vue`、`SelectionStepDetail` の右カラム）**

配置は「企業からのFB」と「このステップのメモ」の間。右カラムはその学生に固有のものを
集めた列で、会社から受け取ったもの（FB）→ 依頼されたもの（アンケート）→ 自分が書くもの
（メモ）の順に並ぶ。


構成：見出し「面接アンケートにご協力ください」／リード文「今後の選考体験向上のため、
率直なご意見をお聞かせください。（所要時間：約1〜2分）」／注記「※回答内容は選考の合否には
一切影響しません。」／5段階スター評価＋自由記述（任意）＋送信ボタン。

- 送信すると `answered` を emit するだけ（実際の保存は行わない）
- 回答済みになったら、カードは「アンケートへのご回答ありがとうございました」の
  控えめな1行表示に切り替える（非表示にはしない）
- 対応するバッジも同時に消える

### 人事FBアンケート（S-12）

**面接アンケート（S-11）と混ぜないこと。** あちらは面接官の**面接**、こちらは
担当人事との**やり取り**が主語。評価軸も母数も次に取る行動も違う。

**表示条件**：選考が終わっている（内定・辞退）とき。判定は
`GET /selection-flow/me` の `hrSurvey.answerable` が持つ。**クライアントで
`selectionStatus` から組み立て直さないこと**（判定が2箇所に散る）。

**配置（`HrSurveyCard.vue`、`StudentHomeView` の独立ブロック）**

選考フローのカードの**直後・外側**に、白カード1枚として置く。

- **★フロー図の中に入れない。** 辞退した学生はフロー図ごと消える（「またご縁が…」の
  1行に置き換わる）が、アンケートは出す必要がある。**辞退者の声こそ改善の材料**であり、
  そこを取らないと「満足した人だけが答えたアンケート」になる
- 選考状況の直後に置くのは、選考が終わった学生にとってこの画面で次に取る行動が
  これしかないから

**構成**：見出し「採用担当の対応についてのアンケート」／リード文（内定と辞退で文面を
分ける。辞退者に「選考お疲れさまでした」は失礼にあたる）／注記「※回答内容は合否・
今後の選考には一切影響しません。回答者が特定されることはありません。」／
3軸（連絡の速さ・説明の分かりやすさ・対応の丁寧さ）の5段階スター評価＋自由記述（任意）
＋送信ボタン。

- **3軸すべてに答えるまで送信ボタンを無効にする。** 部分回答は集計の軸が欠ける
- ★の選択状態は塗りつぶしだけで伝えず、右に「未選択」「4点」を必ず添える（CLAUDE.md §6-13）
- 回答済みかはサーバが持つ（`hrSurvey.answered`）。**ローカル状態にしない**
  （リロードで未回答に戻り、同じ学生に何度も答えさせる）
- 送信は1回きり。押した瞬間にボタンを無効化する
- 回答済みなら「アンケートへのご回答ありがとうございました」の控えめな1行に切り替える

**人事側の集計（`HrSurveyPanel.vue`、監視ダッシュボードの「全社」タブ）**

`/dashboard` に置く。**この画面の主語が「人事の対応品質」だから**で、面接官の面接品質
（S-11）は主語が違うので `/interviews` に分けたまま。エスカレーション表より**下**に置く
（上は「いま手を打つべき案件」、こちらは「振り返って直すところ」）。

- 上：KPI 3枚（回答数・回答率・総合満足度）
- 中：担当者別 総合満足度（横棒・単一色）／評価軸別 平均（横棒・単一色）
  - **どちらも単一色。** 3軸をグループ横棒にしない。3本が必ず隣接するため全ペアの
    色覚検証が要るうえ、軸に「良し悪し」の色が付いて読み違える
  - 「表で見る」に3軸の内訳と選考結果（内定／辞退）別を出す
- 下：スコープ切替（全体／担当者）＋AI要約＋自由記述の原文
  - **棒グラフをドロップダウンに連動させない**（比較が目的の図から比較対象を消してしまう）
  - **絞り込みを画面側でやらない。** 回答が少ない担当者の本文はサーバが落とす
- 回答が下限未満の担当者を伏せていることは、注記として必ず画面に出す
- 個人タブ（`DashboardPersonalPanel`）には3軸の横棒を1枚。**下限未満なら数字を出さず、
  理由を `empty-text` に書く**（黙って空にすると「回答が0件」と読み違える）

## 10. 面接日程予約画面（P3-4）

- 人事側はトーク入力欄の「日程調整を作成」からモーダルを開き、空き枠確認後だけ送信できる
- 学生チャットは候補日時を列挙せず `ScheduleRequestCard` を表示する
- 日程選択は `ScheduleWeekGrid` で日付を列、時刻を行にし、○・×・選択中を文字でも示す
- 選択、確認、完了を別ルートにし、確認画面を開いたときも最新状態を取得する
- 選択画面表示中だけ30秒更新し、タブ復帰・window focusでも再取得する
- Socket購読は画面から `useSchedulesStore.watchRequest()` を呼び、イベント登録自体は `useSocket.js` に置く

## 11. 禁止事項

1. **`v-html` を使わない。** メッセージ本文はテキスト補間で描画する（XSS対策）
2. **`provide/inject` のバケツリレーを使わない**
3. **コンポーネント内で直接 `socket.on()` しない**
4. **列挙値・日本語ラベルを直書きしない。** `shared/constants.js` から取得する
5. **`localStorage` / `sessionStorage` に認証情報を保存しない**（httpOnly Cookie を使う）
6. モバイル対応・レスポンシブは**スコープ外**。1280px 以上の PC 幅のみを対象とする
