# ビジネスロジック仕様

このプロダクトの中核。**ここの挙動がコンセプトそのもの**なので、独自解釈で変更しないこと。
実装先はすべて `server/services/` 配下。

---

## 1. 用件タグ自動判定（P1-5）

実装：`server/services/tagClassifier.js`

### 仕様

```
classify(body: string): TopicTag

1. tag_rules を priority 昇順で取得（起動時にメモリキャッシュ）
2. body に keyword が部分一致したら、その tag を返す（最初のマッチで確定）
3. どれにも一致しなければ 'other' を返す
```

- **学生からのメッセージのみ**判定する。人事の発言には付与しない
- 判定結果は `messages.topic_tag` に保存。同じメッセージを再判定しない

### 設計判断（変更しないこと）

当初は「学生側がタグを選択する」案だったが、
(a) 学生に入力負担を強いる、(b) 誤選択時の責任の所在が曖昧になる
という理由から、**サーバ側の自動判定に一本化**した。**学生UIにタグ選択欄を設けない。**

### キーワード辞書（`tag_rules` の初期データ）

| tag | priority | keyword |
| --- | --- | --- |
| `absence_late` | 1 | 欠席, 休み, 遅れ, 遅刻, 間に合, 行けな, 参加でき, 体調不良 |
| `scheduling` | 2 | 日程, 候補日, 変更, リスケ, 空いて, 都合, 日時 |
| `aptitude_test` | 3 | 適性検査, SPI, テスト, 受検 |
| `result_waiting` | 4 | 合否, 結果, 通過, 選考状況, いつ頃 |
| `question` | 5 | ？, ?, でしょうか, 教えて, 伺い |
| `other` | 99 | （デフォルト。ルール不要） |

## 2. 緊急度算出（P1-6）

実装：`server/services/urgencyCalculator.js`

### 判定表

ルームの最新学生メッセージのタグと経過時間から算出する。**上から順に評価し、最初に該当したものを採用**する。

| # | 条件 | 緊急度 |
| --- | --- | --- |
| 1 | `handling_status` が `done` または `on_hold` | `low` |
| 2 | `topic_tag = absence_late` | **`high`（無条件）** |
| 3 | 経過時間 ≥ 24h かつ `handling_status ∈ {needs_reply, in_progress}` | `high` |
| 4 | `topic_tag ∈ {scheduling, result_waiting}` かつ 経過時間 ≥ 12h | `high` |
| 5 | `handling_status = waiting_student` | `low` |
| 6 | 上記以外 | `normal` |

**#2 の「欠席・遅刻は無条件で緊急」は課題 C-2 への直接の回答**であり、絶対に条件を追加しないこと。

### 再計算タイミング

| トリガ | 対象 |
| --- | --- |
| メッセージ受信・送信時 | 該当ルームのみ（保存と同一トランザクション） |
| 対応ステータス変更時 | 該当ルームのみ |
| **60秒ごとのバッチ** | 全ルーム（経過時間の経過により緊急度が変わるため） |

- バッチは `setInterval` で実装。**値が変化したルームのみ** UPDATE し、`room:updated` を配信する
- 変化がないルームにイベントを飛ばさない（無駄な再描画を防ぐ）

## 3. 経過時間バッジ / SLA（P1-4）

| 経過時間 | 表示 |
| --- | --- |
| < 12h | 通常表示（グレー） |
| ≥ 12h（`SLA_WARN_HOURS`） | **黄**バッジ |
| ≥ 24h（`SLA_ALERT_HOURS`） | **赤**バッジ |

- 基準時刻は `rooms.last_student_message_at`
- `handling_status` が `done` / `waiting_student` の場合は**バッジ非表示**
- 表示形式：`3分` / `2時間` / `1日3時間`
- **クライアント側で1分ごとに再計算**して表示更新する（`composables/useElapsedTime.js`）。サーバへの再取得は不要

これが課題 C-1「合否連絡が1日遅れた」への直接の回答となる中核機能。

## 4. 対応ステータスの自動遷移（P2-3）

実装：`server/services/statusTransition.js`

**手動更新を強要しないことが定着の鍵。** 自動遷移を確実に実装すること。

| トリガ | 遷移前 | 遷移後 |
| --- | --- | --- |
| 人事がメッセージを送信 | `needs_reply` / `in_progress` | → `waiting_student` |
| 学生がメッセージを送信 | `waiting_student` / `done` | → `needs_reply` |
| いずれの場合も | `on_hold` | **遷移しない** |

- 自動遷移後も、人事は手動で任意のステータスに上書きできる
- 遷移が発生したら `room:updated` を全 hr に配信する
- 手動変更時のみ `messages` に `type='system'` のシステムメッセージを記録する（自動遷移では記録しない。ノイズになるため）

## 5. 定型文の変数展開（P2-1 / P2-2）

実装：`server/services/snippetRenderer.js`（またはクライアント側で展開してもよいが、ロジックは1箇所に）

### 対応変数

| 変数 | 置換元 |
| --- | --- |
| `{学生名}` | `users.display_name`（学生） |
| `{面接日時}` | `students.next_interview_at` |
| `{会議室}` | `students.next_interview_room` |
| `{面接官}` | `students.interviewer` |
| `{担当者名}` | ログイン中の人事の `display_name` |
| `{選考段階}` | `students.selection_status` の表示名 |

### ルール

- 値が未設定の変数は `【未設定：面接日時】` と**赤字で残す**。空文字で置換しない（送信前に気づけるようにするため）
- **展開結果は必ず入力欄に挿入し、送信前に自由に編集可能**にする。展開と同時に送信してはいけない（「定型文の冷たさ」への配慮）
- 日時のフォーマットは `8月7日（金）14:00`

## 6. 一覧のデフォルトソート（P1-7）

```
1. is_pinned DESC              -- ピン留めが最上位
2. urgency                     -- high → normal → low
3. last_student_message_at ASC -- 経過時間が長い順
```

- 切替可能なソート：最終メッセージ時刻順 / 経過時間順
- フィルタ条件とソート条件は Pinia に保持し、ルーム切替で失われないこと

## 7. AI 緊急度判定（P3-1・採用した場合のみ）

実装：`server/services/aiClassifier.js`

- P1-6 のルールベースを Gemini API に置換し、「用件タグ・緊急度・1行要約」を JSON で取得する
- 受信箱上部に「今日の要対応3件」を自動要約して表示する

### フォールバック要件（必須）

**外部API依存がデモ中の最大のリスク。以下を必ず実装すること。**

1. **タイムアウト3秒**。超過したら即座にルールベースへフォールバック
2. API エラー・レスポンス不正時もルールベースへフォールバック
3. **`GEMINI_API_KEY` が未設定でも全機能が正常に動作すること**
4. 結果は `messages.topic_tag` にキャッシュし、同一メッセージへ再問い合わせしない
5. AI 呼び出しはメッセージ保存トランザクションの**外**で行い、失敗してもメッセージ保存自体は成功させる

受入条件：**API を意図的に停止しても、アプリが停止せずルールベース判定で動作を継続すること。**
